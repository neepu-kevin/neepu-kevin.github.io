SKILL.state:Scalable Long-Horizon Agent Skills

Posted on 2026-10-23 Edited on 2026-10-25 In 论文阅读 Views: Word count in article: 2.8k Reading time ≈ 9 mins.

从执行历史到当前状态

在长任务中，Agent 需要持续接收工具结果，并根据这些结果决定下一步动作。一种直接的实现方式，是把用户请求、工具调用、观察结果和中间推理不断追加到上下文中。下一次调用模型时，再把此前的记录一起输入。

这种方式能够保留执行经过，但也带来了一个问题：任务越长，模型需要重新阅读的历史就越多。其中有些信息仍然有效，有些已经被后续操作覆盖，还有一些只是当时推理过程中产生的临时判断。模型不仅需要决定下一步做什么，还需要从这些记录中重新确定当前状态。

SKILL.state 关注的就是这部分执行机制：能否直接维护一份当前状态，让下一步决策不再依赖完整历史的重复输入？

历史记录与执行状态

论文在 SkillExecBench 中设置了一个软件仓库环境，其中包含 Git 分支、提交、PR 和 CI 测试状态。这些信息存在依赖关系：合并一个 PR，会改变目标分支及依赖它的 PR 的状态。论文 §4.1

沿着这个例子来看，执行历史和当前状态承担着不同的作用。历史记录描述此前进行过哪些 Git 操作；当前状态则需要表达这些操作之后，分支、提交、PR 和测试之间仍然有效的关系。后续决策需要依据的是这些当前事实，而不能直接沿用已经失效的旧判断。

如果每一步都输入完整历史，模型就需要反复完成这项重建工作。随着历史增长，输入消耗随之增加，过时观察和无关内容也可能干扰后续判断，造成上下文污染。

摘要可以缩短历史，但“把执行经过压缩成文字”和“显式维护当前状态”依然有区别。前者仍可能要求模型从描述中推断当前事实，后者则将这些事实作为运行时直接维护的对象。

SKILL.state 采用的是后一种方式：将执行状态结构化，每一步只向模型提供固定的执行流程、当前状态以及最新观察。

一轮执行需要哪些信息？

先看论文的架构对比图。左侧把历史对话、过去的观察与推理继续放入上下文；右侧则以执行状态承接需要跨步骤保留的信息。

SKILL.state 将第 t 步的执行上下文表示为：

At = (P, Σt, Ot)

其中：

  • P 是固定的 Skill 执行流程说明，规定任务应遵循的程序。
  • Σt 是当前的结构化执行状态，保存后续执行所需的信息。
  • Ot 是环境返回的最新观察，为当前决策提供新信息。

这三个部分各有作用。执行流程不会因为任务多走了几步就不断增长；状态需要随着任务推进而更新；观察则告诉模型刚刚发生了什么。

回到软件仓库环境，关键并不是把所有 Git 操作换成 JSON 保存，而是维护操作之后仍然有效的状态关系。模型将当前状态与最新观察结合，再决定哪些事实需要更新，以及下一步应采取什么动作。

推理怎样转化为状态？

接收执行上下文后，模型生成：

(Rt, ΔΣt, at)

Rt 是本步的推理过程，ΔΣt 是结构化状态增量，at 是接下来要执行的动作。

运行时验证状态增量，并将其应用到当前状态：

Σt + 1 = Σt ⊕ ΔΣt

论文中的 ⊕ 是带有 null 删除语义的字典合并操作，用于更新或删除状态字段。完成状态更新后，运行时执行动作，并在下一轮接收新的观察。论文 §3.2

下面的算法将整个循环串了起来：接收观察、构造输入、生成推理与更新、验证更新、写入状态，最后执行动作。

这里需要区分的是推理的生成与保留。模型在当前步骤仍然可以进行多步推理；当状态更新经过验证并应用之后，中间推理就不再进入后续 Prompt。

留下来的是后续执行需要依赖的状态，推理则作为生成本次更新和动作的中间计算。

状态结构由谁决定？

SKILL.state 使用预先定义的 Schema 约束状态，而不是让模型每一步自由决定记录格式。论文中的 Schema 按领域编写，并非每个任务实例都重新设计一份。

例如，InterCode CTF 使用同一组五个字段：discovered_flags、tested_hypotheses、active_files、working_dir 和 cmd_summary。论文 §3.1

这些字段也帮助我们理解结构化状态的含义：它保留的是与继续执行有关的事实和进度。状态需要足够明确，才能在不重复输入完整历史的情况下，为下一步提供依据。

为什么累计输入规模能够降低？

传统历史追加方式的开销，既来自历史本身增长，也来自旧内容在后续步骤中被反复输入。

为了说明这个过程，沿用一个简化的计算：设固定提示词长度为 p，每一步新增历史长度为 h，总执行步数为 T。第 t 步的输入长度为：

Lt = p + (t − 1)h

同时，这里讨论的是累计 Prompt 输入规模，不是 Agent 整体执行的时间复杂度。工具调用和模型生成等成本，不包含在上述求和中。

实验在验证什么？

仅仅让输入变短，还不足以说明一种执行机制有效。更关键的问题是：减少历史之后，模型能否保留完成任务所需的信息，并据此作出正确决策？

论文使用 SkillExecBench 和公共交互基准进行评估。SkillExecBench 包含维护 500 个独立货架的 Warehouse Management，以及前面介绍的软件仓库环境；公共基准包括 InterCode CTF，以及 Sierra τ-Bench 的 Retail 和 Airline 任务。

实验模型包括 Gemini-3-Flash、Gemma-4-31B-it 和 Qwen-3-8B-it。对照方法包括 Prompt（ReAct）、Memory（Summarization）、Stateful（LangGraph 风格），以及 Truncated、Summary-capped 和 LLMLingua 等补充对照。这里应把这些名称理解为论文中的具体实现与设置，而不是对所有同类框架的统一评价。

可以从五个问题理解这些实验的安排：

实验 关注的问题
Long-Horizon Execution Scaling 执行步数增加后，准确率、平均输入与累计消耗怎样变化？
Context Corruption / Noise Robustness 无关信息会不会干扰状态维护与后续决策？
State Recovery 接收到纠正信息后，Agent 能否及时修正状态？
Public Interactive Benchmarks 在公共交互任务中，方法是否仍然有效？
Budget-Matched Controls 收益来自输入缩短，还是来自保留信息的方式？

论文报告的总体结果是：SKILL.state 在长任务中保持了较好的准确率，同时降低累计消耗；在噪声、恢复与公共交互任务中，也体现了结构化状态的作用。不同设置的具体结果应结合原论文实验部分阅读，不能由此推成所有任务上都会得到相同收益。

其中，我认为预算匹配对照最贴近这篇工作的核心问题。如果仅仅截短输入就能达到同样效果，那么状态结构本身的作用就不明显；而简单截断或压缩不能保证准确率，说明我们还需要关心：哪些信息被留下，以及它们是否足以支持之后的执行。

因此，这篇工作的意义不能只用“节省 Token”概括。减少重复输入和维持有效状态，需要放在一起理解。

状态能够替代历史的前提

读到这里，一个自然的问题是：只要把历史整理成结构化状态，就可以放心丢弃其余内容吗？

论文并没有把这个前提视为无条件成立。它在限制部分指出：预先无法确定 Schema、早期信息的重要性直到后续才显现，或任务本身要求输出历史轨迹时，这种做法存在边界。论文 §7

这也提醒我们区分两个要求。一方面，状态不能无止境增长，否则输入有界的条件不再成立；另一方面，状态又必须保留未来决策所需的信息，否则减少历史可能以丢失依据为代价。

因此，如何选择状态内容、怎样正确更新状态，是这类执行机制本身需要承担的工作。结构化提供了明确的表示方式，但它不能自动保证每个需要保留的事实都被正确识别。

总结

对我来说，SKILL.state 最值得记住的是它对执行信息的重新组织：把不断累积的历史，转为显式维护、随执行更新的当前状态。

在每步输入长度有固定上界的条件下，这种组织方式可以将累计 Prompt 输入规模从 O(T2) 降至 O(T)。与此同时，Agent 仍然进行推理和工具调用，只是不再把所有中间过程永久带入后续输入。

从最初的问题回看，长任务确实需要延续过去的信息，但需要延续的内容，应当由未来的执行需求来决定。关键是把仍然有用的事实保留下来，并在它们改变时及时更新。
