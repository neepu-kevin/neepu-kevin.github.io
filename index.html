SKILL.state Scalable Long-Horizon Agent Skills

Posted on 2026-10-23 In 论文 Word count in article: 1.3k Reading time ≈ 4 mins.

Introduction

As agents increasingly execute long-running procedures, execution itself becomes a systems problem rather than purely a reasoning problem.

随着 Agent 执行的任务越来越长，任务执行本身逐渐成为一个系统问题，而不再只是一个推理问题。

Agent 在完成任务时，一种简单而常规的方法是将 System Prompt、User Prompt、Tools 调用、Observation 和中间 Reasoning 过程完整加入上下文。随着执行步骤增加，历史记录不断增长，不仅造成 Token 消耗增加，也可能因为过时信息和无关内容导致 Context Poisoning。

即使采用 Memory（Summarization）对历史进行压缩，本质上仍然依赖历史文本重构当前执行状态。

Future decisions are conditioned on textual reconstructions of past execution rather than an explicit representation of the current execution state.

本文提出 SKILL.state，通过显式维护结构化执行状态，替代不断累积的完整历史。每一步只给 LLM 提供执行流程、当前状态和最新观察结果，而不再重复输入所有历史推理与工具调用记录。

核心思路：用当前执行状态代替历史执行过程。

SKILL.state

Runtime Architecture

Figure 1. Traditional Skill Execution 与 SKILL.state 架构对比。

SKILL.state 将每一步的 Prompt 分为三个部分：

Pt = (P, Σt, Ot)

其中：

  • P：固定的 Skill 执行流程说明。

  • Σt：第 t 步的结构化执行状态。

  • Ot：当前最新的 Observation。

LLM 根据这三个部分进行 Reasoning，输出当前状态的更新内容 ΔΣt 和下一步 Action at。

状态更新过程为：

Σt + 1 = Σt ⊕ ΔΣt

运行时验证并更新状态，执行 Action，再获取下一轮 Observation。

需要注意，SKILL.state 并没有舍弃 Reasoning 和 Action 的执行，而是舍弃后续步骤不再需要的中间推理历史。

Structured Execution State

SKILL.state 通过预先定义的 Schema 来约束状态结构，记录任务执行所需的关键信息。

例如在软件仓库任务中，可以保存当前 Branch、Commit、PR 状态和测试结果，而不是每次都重新读取之前所有 Git 操作的对话。

这样，LLM 每一步都能直接获得当前任务状态，而不必从冗长的历史中重新推断。

Complexity Analysis

传统 Agent 每一步都会重复输入之前累积的历史。假设固定提示词长度为 p，每一步新增历史长度为 h，总执行步骤为 T：

Lt = p + (t − 1)h

累计输入规模：

SKILL.state 每一步只提供固定执行说明、结构化状态和最新 Observation。在这些内容长度存在固定上界 K 的条件下：

Lt ≤ K

因此，在状态大小有界的条件下，累计 Prompt 输入规模由 O(T2) 降低至 O(T)。

这里讨论的是 Prompt 输入规模，而不是 Agent 整体执行的时间复杂度。

Evaluation Benchmarks

论文使用两类 Benchmark 验证方法：

SkillExecBench（Controlled Diagnostic Testbed）

  • Environment 1：Warehouse Management，500 个独立货架，测试长任务中的状态维护。

  • Environment 2：Software Repository，Git 分支、PR 和 CI 等存在复杂依赖关系的状态。

Public Interactive Benchmarks

  • InterCode CTF (Yang et al., 2023)

  • Sierra τ-Bench (Yao et al., 2024)：Retail、Airline

Models： Gemini-3-Flash、Gemma-4-31B-it、Qwen-3-8B-it。

Baselines： Prompt (ReAct)、Memory (Summarization)、Stateful (LangGraph)，以及用于补充对照的 Truncated、Summary-capped、LLMLingua。

Metrics： Task Accuracy / Success Rate、Average Prompt Size、Total Token Cost。

Experiments and Results

实验 要回答的问题 主要结论
Long-Horizon Execution Scaling 执行步数增加后，准确率、Prompt 长度与累计消耗如何变化？ SKILL.state 在保持较高准确率的同时，显著降低累计 Token 消耗。
Context Corruption / Noise Robustness 加入大量无关信息后，Agent 的执行表现是否稳定？ 结构化状态能够减少无关历史信息对后续决策的干扰。
State Recovery 外部环境发生变化后，Agent 能否及时纠正执行状态？ 接收到纠正信息后，可以直接更新状态，减少额外恢复步骤。
Public Interactive Benchmarks 在公共交互任务中，SKILL.state 是否仍然有效？ 在 InterCode CTF 和 τ-Bench 测试中取得了更高的成功率。
Budget-Matched Controls SKILL.state 的收益只是来自 Prompt 变短，还是来自结构化状态对关键信息的保留？ 简单截断或压缩上下文并不能保证准确率，关键在于如何保留和组织执行信息。

实验主要说明，减少 Token 消耗并不是 SKILL.state 的全部收益，更重要的是通过结构化状态保留对未来决策有用的信息。

Conclusion

SKILL.state 的核心是将不断增长的历史对话转变为显式、可更新的执行状态。

在状态大小有界的条件下，将累计 Prompt 规模从 O(T2) 降低至 O(T)，同时在长任务执行、噪声干扰和状态恢复实验中表现出较好的准确率与效率。

对我而言，这篇论文最值得记住的是：

Agent 不需要在每一步重新阅读所有执行历史，而是需要准确知道当前处于什么状态。
